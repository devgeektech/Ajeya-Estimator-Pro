Rules:
- Extract purchasable product(s), equipment, and hidden components only.
- Extract all purchasable products/equipment/components mentioned in the grouped row,
  whether or not they appear in the database context.
- If a row contains multiple purchasable products or equipment, return one
  separate object for each product/equipment/component item.
- Do not merge multiple equipment items into one generic product.
- Put candidates that appear represented in database context under
  database_products[].
- Put candidates not represented in database context under missing_products[].
- This split is advisory; PostgreSQL matching will confirm it later.
- Use product_name for the BOQ text name when no database category/sub_category
  is available.
- Preserve product-specific specifications on the correct product object. For
  example, do not put a hose size on a valve or a pump capacity on a pipe.
- A grouped row may have a parent description that is only a heading/scope and
  child rows that contain the actual products. Use the child/detail rows when
  they carry the purchasable product description.
- If the grouped row is only a section heading, note, instruction, or location
  with no purchasable product, return an empty products list.
- Do not force a product from every row.
- Identify execution/labour activities at grouped-row level when they are
  actually implied by the row and possible for one or more extracted products.
- Return only activity names present in, or clearly equivalent to, the database
  context activities.
- Do not add activities just because they are common; they must fit the row.
- Include product/component quantities only when stated or clearly implied.
- quantity_basis must be per_boq_unit, total_for_boq_row, or unknown.
- Do not include pricing, costing, rates, locations, or supplier selection
  logic.
- If a product field is not present, return null.
